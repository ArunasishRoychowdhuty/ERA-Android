# v0.7 — snapshot-bound Accessibility approvals

## Problem addressed

Before this revision, a pending action checked that the user returned to the expected app and that a semantic selector still found a target. It did not require the entire current UI tree to match the exact screen state that had been reviewed. A control could therefore remain textually similar while surrounding page state changed.

## New approval binding

When an approval is created, ERA calculates a SHA-256 ID over:

- The target package name.
- The complete serialized root Accessibility tree.
- The node count.
- The truncation flag.

The capture timestamp is excluded so an unchanged tree has a stable identity. UI text, content descriptions, hints, resource IDs, roles, visibility/enabled/action flags, hierarchy and bounds are included through the serialized tree. The hash is conservative: even a benign visible tree change invalidates the pending approval.

When the ERA overlay is tapped, the service:

1. Checks that screen-inspection consent is still enabled and the device is unlocked.
2. Captures the current active window.
3. Checks the expected package.
4. Recomputes the tree fingerprint and compares it with the exact reviewed fingerprint.
5. Cancels the action if the fingerprint is absent or differs.
6. If the snapshot matches, resolves the semantic target again and checks visibility, enabled state, action support and existing consequential/password policies.
7. Consumes and clears the stored approval payload before dispatching the single approved action.

The pending selector, entered text, expected package, fingerprint and creation timestamp are cleared atomically on consumption, cancellation or expiry. The result message is retained separately.

## Test coverage

The pure Kotlin smoke suite checks that identical serialized trees return identical IDs, changed tree content returns a different ID, a different package returns a different ID, and fingerprints are 64-character lowercase SHA-256 hex strings.

## Limits

- This protects the existing one-shot Accessibility action path; it does not mean the autonomous `BoundedAgentRuntime` has been wired into Android.
- A SHA-256 fingerprint proves equality of the serialized local tree, not the truth of app semantics. Labels can be misleading, controls can have hidden side effects, and Accessibility metadata can be incomplete.
- A rapidly changing page may cause false cancellation. This is intentionally safer than reusing an approval against a different screen.
- If an app does not expose useful Accessibility nodes, ERA may be unable to act.
- No Android SDK/Gradle build or physical Android 15 test has been run here.
